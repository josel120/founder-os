# T-061: Fix lost client updates after server actions and navigations

- Status: done
- Owner: claude
- Size: M
- Depends on: none

## Goal
After a server action (capture, edit, convert) or a link click, the page sometimes never shows the result until a reload: a new problem is missing from the list, an edited title stays old, or a navigation never commits. The owner sees stale or stuck pages; E2E specs that rely on in-place updates flake (T-054 note, `research.auth.spec.ts:91`, `workflows.auth.spec.ts:50,92`, the first T-051 draft in PR #37).

## Evidence (PR #37 investigation, 2026-09-26)
- Reproduction against `next start` with the E2E owner: load `/private/problems`, capture a problem, wait for "Problem saved privately.", then wait 4 s for its link. It is missing in 1–18 of 30–50 tries. The rate grows with the list's RSC payload (138–250 KB at ~400 problems) and with concurrent load. Once lost, the update never arrives (waited 20 s).
- Instrumenting Next 15.5.26 `app-router-instance.js` showed the server action is **applied**, not discarded (no navigation interferes).
- In one stale case the action response carried the full tree (206 KB, `x-action-revalidated: [[],1,0]`). In others the browser reported the action POST `net::ERR_ABORTED` ~80 ms in, after the first chunk (the action result) but before the tree. Chrome also marks most RSC GETs `ERR_ABORTED` about 10 ms after headers, including successful ones.
- The server streams complete in 20–90 ms under curl (with and without gzip). `compress: false` did not help (18 of 50).
- Ruled out: the router queue discarding the action, the server holding streams open, compression, and missing page chunks.

- Root cause: a React bug in the build Next 15.5.26 vendors for the App Router (`19.2.0-canary-0bdb9206-20250818`; the installed 19.3.0 is unused there). A transition suspends on a lazy Flight chunk and yields; the row arrives meanwhile and stays `resolved_model`. On resume React attaches a ping, Flight's `then()` fires it synchronously inside the render, and `pingSuspendedRoot` drops it, so the lane stays suspended forever. Proven by instrumenting the built chunk (root lanes, ping log) and by a one-line fix probe. Details: ADR-017.
