# T-091: Say why the AI provider refused a run

- Status: review
- Owner: claude
- Size: S
- Depends on: T-089

## Goal
The first production run failed with "The AI provider did not answer": every non-auth, non-rate-limit provider error (no credit, unknown model, bad request, overload) was reported the same way and nothing was logged, so the cause could not be found. The owner now gets an actionable message and the server logs the provider's status and error type.

## Acceptance criteria
- [x] Provider errors are classified from the HTTP status and the provider's error type: billing (402, `billing_error`, credit-balance 400), model not available (404), bad request (other 400), overloaded (529), server error, network/timeout.
- [x] The owner sees a specific message for each; the stored `ai_run.error` code stays within the existing CHECK list (no migration).
- [x] One log line per provider refusal with only the HTTP status and a well-formed error-type code (`[a-z_]{1,40}`, else `unknown`); never the message, body, key or prompt.
- [x] Tests added or updated for changed behavior
- [x] `pnpm typecheck`, lint on changed files and unit tests pass (exit codes in handoff)
